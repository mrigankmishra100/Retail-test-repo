1. System map

The browser calls one application backend. The backend authenticates the session, selects a service by route and role, and invokes the appropriate local graph. Model tool calls are validated and executed through trusted tool bindings. Oracle owns commercial facts and approvals.

A. Retail conversation — model-directed, read-only

RetailConversationService loads owned history, optionally attaches authoritative workflow facts, and invokes build_retail_conversation_graph. The graph contains llm and read_only_tools. The model selects tools from advertised schemas; the application validates names, arguments, call IDs and limits before executing them. Tool output returns to the model for synthesis.

  • Limits: four model calls, eight function calls and 100,000 context characters per graph invocation.
  • With RAG enabled, the first response requires native File Search. A follow-up model call can request current inventory/supplier facts before the final answer.
  • The conversation graph has no LangGraph checkpointer. Oracle chat history and optional OCI conversation state provide continuity; the current local configuration uses Oracle history, with OCI conversation state disabled.
  • Model changes reset conversation context. Typed approval/send instructions do not authorize business actions.

B. Retail replenishment — deterministic control flow

START → analyze
  ├─ no risk / insufficient history → END
  └─ assessed → compare → explain
       ├─ no feasible supplier → END
       └─ select [interrupt: human selection]
            → create → prepare → approval [interrupt: stored manager decision]
                 ├─ rejected → END
                 └─ approved → dispatch
                      ├─ sent / reconciliation required → END
                      └─ blocked / pending → wait_delivery [interrupt]
                                             → dispatch after explicit resume

RetailWorkflowService authenticates ownership, reserves a deterministic thread ID from the session/idempotency key, acquires a single-writer cache lock and compiles the graph with a cache checkpointer. analyze reads inventory; compare calculates policy-backed feasible quotes; explain optionally asks the selected model for an advisory. Selection, case creation, approvals and sending follow fixed rules.

prepare freezes the commercial draft and email narratives for review. approval reads the persisted Oracle decision; resume text is ignored as authority. dispatch calls the controlled notification tool only after the required stored decision.

START → receive
  ├─ completed → memory → END
  ├─ rejected → END
  ├─ already approved → dispatch
  ├─ response already sent → complete → memory → END
  └─ inventory → policy → quote → draft → approval [interrupt]
       │                                  ├─ rejected → END
       └─ blocked → wait_review            └─ approved → dispatch

                          ↓                     ├─ pending / blocked → wait_delivery
                        receive                 │                         ↓ explicit resume
                                                │                       dispatch
                                                └─ reconciliation required → END

The supplier service binds the session to its assigned supplier and visible case. It checks available stock, extracts the correct supplier policy, recomputes the quote and compares it with the saved draft. Changed/infeasible facts block review. Draft responses reuse stored terms or deterministic rendering. This graph has no independent model node; switching a chat model does not alter these fixed checks.

4. Tools, data access and RAG

Model-visible read-only tools

get_inventory_risk; get_item_sales_history; get_suppliers_for_item; get_supplier_policy; draft_supplier_email; get_approved_memory; query_retail_data when enabled.

Workflow-only operations

Trusted retail/supplier bindings can create/prepare cases, calculate quotes, retrieve scoped history and invoke controlled send/close tools. These are not all advertised to the chat model.

FastMCP

TOOL_FUNCTIONS is the application’s tool registry. Local bindings call these functions directly. Optional remote MCP uses the hosted MCP boundary and trusted delegated session context.

Automatic tool routing means the model chooses from the provided tool schemas; Python validates and executes the selected function. It does not mean OCI discovers arbitrary application tools or agents automatically. Built-in File Search is executed by OCI within the model request; retail functions execute through the application.

Two policy paths serve different purposes

  • Chat RAG: uploaded policy PDFs in configured OCI vector stores → native File Search → citations and advisory answer. In native RAG mode the graph removes the competing get_supplier_policy function from the advertised tool list. The separate search_policy_documents function/adapter still exists, but is not in the current conversation allowlist.
  • Commercial validation: PolicyService reads the complete supplier PDF from Object Storage, with same-supplier local PDF fallback, validates identity/hash and parses terms. Deterministic quote logic uses these full-policy facts. A retrieved passage does not replace commercial validation.

What “NL2SQL” currently means

The model selects a constrained plan such as inventory, sales_summary or supplier_options. EnterpriseAINL2SQLClient validates tables, sort, identifiers and row limits, then calls a fixed SELECT operation in OracleDatabaseClient. It does not currently call a separate managed NL2SQL model or execute arbitrary model-written SQL.

Sources: agents/tool_access.py; mcp/tools.py; enterprise_ai/nl2sql.py; services/{policy,policy_terms,policy_search,supplier}.py.

  • Live directory: AgentRegistryService reads/writes Oracle registry rows. Fields include name, type, endpoint, description, active flag and timestamps. Oracle enforces one active destination for each routed RETAIL/SUPPLIER type.
  • Per-call resolution: RemoteAgentClient resolves the endpoint before each invocation. Invalid/multiple destinations and registry failures fail closed; absence of an active entry permits the configured endpoint fallback. Existing local mode remains local.
  • Transport: custom agent-base64-v1 envelope, HMAC signature/key proof, audience/session validation, timestamp/nonce handling, size limits and no automatic action replay. This is not standard A2A Agent Card/message/task interoperability.
  • Separate adapter: EnterpriseAIRegistryClient contains configured Oracle resource references for two agents and an MCP server. It is not a live OCI discovery client.
  • Observed local deployment: Retail Agent is active but executes locally; Supplier Agent is registered as CUSTOM, which is directory-only. No remote agent roles are configured in the local settings.

Management APIs: GET/POST /registry/agents and POST /registry/agents/{id}/activate or /deactivate. They require an existing application session; both POC workspace roles currently have management access. They are not substitutes for hosted-worker credentials or availability checks.

8. Live activity, evaluation and monitoring

New expandable Agent Chat activity

  1. When Agent Chat is active, the frontend assigns an X-Activity-ID to supported chat, workflow, decision, draft and dispatch requests. Background case/status reads are excluded.
  2. ActivityMiddleware creates a request context; session authentication binds it to the authenticated owner. Instrumented spans record graph nodes, model calls, tool execution, database access, policy storage and hosted-agent routing.
  3. The browser polls GET /activity/{id} roughly every 600 ms after a response to the previous poll. Each request starts as one collapsed line, expands during execution, and retains measured steps after completion. A final read captures fast steps between polls.
  4. Graph interrupts display as waiting. Exceptions display failed steps without exception bodies. Native built-in tool calls are reported after OCI returns them; their private internal progress is not observable.
  5. Activity never resubmits business requests. Missing metadata does not block the result. A client timeout is shown as an interrupted connection requiring a status check, not proof that an action failed to execute.

Activity is transient, process-local POC telemetry: ten-minute retention, 300 tracked requests per process, 200 steps per request, and the latest eight requests in the chat view. Multi-worker deployments need sticky routing or a shared activity store. Remote worker internals are not streamed back: the backend can show registry lookup and the hosted invocation boundary. SQL, parameters, prompts, answers and credentials are excluded from this feed.

Three different evidence layers

  • Evaluation: provider-reported tokens and citations; measured latency; tool success and optional expected-term checks; reviewer ratings. Expected-term matches and speed are not factual-correctness scores. Comparisons use fresh contexts and shared read-only permissions.
  • Application traces: session-owned saved run events and live execution metadata. The trace explorer groups events by run. Workflow AI metrics are retained when model calls were recorded.
  • OCI operations: centralized structured logging across app sessions, plus official Usage API compartment billing. Billing totals are not per-request model costs. Unavailable official costs are shown as unavailable, not estimated.

Detailed automatic LangGraph/LangSmith exports are explicitly suppressed around sensitive graph execution. A LangSmith adapter exists but is disabled in current settings. Managed Langfuse and OCI Managed LangChain are not established integrations in this runtime.
