# Distributor App REST integration

Updated 2026-10-19 for the owner's documented API. The adapter passed a live
authenticated request; deploying this code and testing from OCI remain pending.
This is custom REST delegation, not standard A2A. The service uses AWS inference
but is hosted on an OCI VM; neither location requires an AWS SDK in our app.

## Actual contract

Register the full POST endpoint:

```text
https://150.230.130.251:8081/aws-app/api/v1/answers
```

Headers: `Authorization: Bearer <integration token>`, `Content-Type: application/json`
and `Accept: application/json`. The website's login password is not this API token.
The app does not use the website-only `/api/questions/ask` route.

```json
{"question":"Compare BlueDart and Delhivery delivery timelines."}
```

Only question text is sent. No supplier ID, transcript, hidden prompts or OCI
credentials are automatically attached. Questions should include the relevant
BlueDart, Delhivery, Ekart or DTDC names and delivery context. The remote token
controls document access; the remote API does not implement supplier-specific
authorization. Our supplier session, tool permissions and connection isolation
remain enforced locally and across the signed MCP boundary.

HTTP 200 JSON response includes:

| Field | Expected value |
| --- | --- |
| `id`, `document_id`, `request_id` | UUID strings generated by the remote service |
| `question` | Exact echoed question |
| `answer` | Nonempty answer, up to 16,000 characters |
| `sources` | Up to 20 objects with `source_id`, `document_name`, `excerpt`, nullable `page` and `score` |
| `answer_status` | `answered` or `insufficient_information` |
| `demo_data` | Boolean; true for the current fictional knowledge base |
| `model_id`, `knowledge_version` | Nonempty strings |
| `latency_ms`, `created_at` | Nonnegative duration and timestamp |

Additional fields are ignored for forward compatibility. Total response size is
limited to 64 KiB, with a 30-second network budget. Correlation uses the echoed
question, since request IDs are generated remotely. An insufficient-information
answer is a valid response, not a service outage. The API's `answer` is displayed
directly in supplier chat, preserving text, line breaks and inline source references.
There is no supplier-model rewrite or app-added demo/booking disclaimer. The graph
ends after a successful delivery result; if a turn requests multiple delivery
answers, their original texts are separated by a blank line. Sources and demo
metadata remain in the tool result and tracing. Text already inside the remote
answer, including any disclaimer supplied by that API, is not removed. Chat
renders the text as Markdown and labels it **Delivery agent response**.

This is document Q&A only. It does not book deliveries, provide live tracking,
approve orders or guarantee real distributor terms. The current document is
`Distributor_Knowledge_Base_DEMO.md`, version `demo-2026-10-19-v2`.

## Setup in the Retail App

1. Use the `R-I-Cloudworld` branch and rebuild **all five source
   services** from `deployment/source-build.json`. Start a fresh dashboard source
   inspection so it pins the new commit instead of resuming an older build.
2. Sign in as the supplier who will use the API. In **Agent registry**, choose
   **Custom**, enter any display name and the complete URL above, and select Active.
   The always-visible **Bearer token (optional)** field accepts the token value
   or `Bearer <token>`. Click **Register
   agent** once to create the entry and save its private session connection.
   Leave the field blank only when the API permits unauthenticated access; no
   Authorization header is sent in that mode. The current distributor API requires
   its integration token. Registration does not call the remote API or validate it.
   If connection saving fails, the entry remains and the UI explains how to retry
   on that entry without registering a duplicate. Supplier Custom registration
   automatically selects that API for delivery questions, replacing the previous
   session selection. Existing DELIVERY entries remain supported; names do not determine routing.
3. To connect an existing entry or a new login session, expand **Connect delivery
   API**, enter its token if needed and choose **Connect for this session**.
   Submitting a blank field explicitly replaces any saved token with an unauthenticated
   connection. This selects that entry for delivery questions, replacing this
   session's previous destination and token together. Names do not control routing.
   Do not include `Authorization:` in the input. Reconnect after session expiry,
   a new login, or upgrading the old connection-cache format. Other supplier
   sessions retain their own connections.
   The token field clears after submission. A **Connected for this session** badge
   beside the registered agent confirms server-side storage and remains visible
   after a page refresh. **Connection saved — activate this agent** means the saved
   connection cannot be used until the entry is active. Errors appear beside the
   token input; **Refresh connection status** checks the server without sending a
   question to the distributor. Connection status does not validate the remote
   token: the first delivery question checks API authorization.
4. In supplier chat ask: “Compare BlueDart and Delhivery delivery timelines.”
   Explicit delivery/distributor questions use the current session selection directly
   after guardrail checks. Connecting takes effect in an existing chat without a refresh.
   Without an available connection, chat explains its supported scope without setup
   instructions. Configuration questions can still ask for setup help explicitly.
5. Expand activity to see `ask_delivery_agent` and **Calling delivery agent via
   REST**. Check that the displayed answer matches the API's `answer`, including
   its inline source references and without app-added commentary.
6. Deactivate the registry entry to block subsequent calls or Disconnect to delete
   the session token. Already in-flight calls may finish.

For local testing, restart the backend and run the frontend from this checkout.
The connection-status UI requires the matching backend's new
`GET /registry/agents/delivery-connection` route; refreshing only the frontend
while an older backend is running is insufficient. Status responses contain no
token, are session-authorized, and are marked `Cache-Control: no-store`.
No token needs to be put into source, `.env`, image archives or GitHub.

## Deployment and security boundaries

- OCI ApplyGuardrails screens supplier chat before inference and tool execution
  when enabled by the supplier/MCP image chat defaults. Runtime IAM is required.
- Registry endpoint and token are server-owned and never model tool arguments.
  Only a supplier session can connect and invoke this tool; retail chat cannot.
- The selected registry ID, endpoint and token stay together in the private
  connection with an explicit `auth_mode` (`bearer` or `none`). Missing bearer
  credentials never automatically downgrade to unauthenticated requests. The
  saved connection expires with its session and is bound to the session and supplier. Current registry
  status/type and the exact endpoint are checked before every call. An endpoint
  change requires reconnecting; an inactive entry is not invoked.
  The token is not placed in browser
  storage, registry rows, model messages or traces. Disconnect deletes it; logout
  invalidates the session and connection data expires at its TTL.
- Configured Redis is used when available. Resource-principal deployments without
  Redis share delivery connections through the existing Oracle app database.
  The additive `delivery_connections` table is created automatically on first use;
  the reviewed dashboard grants CREATE TABLE to the app schema. If that grant was
  removed, its owner can apply migration 006 once. Expired records are excluded on
  every read and purged on subsequent connection operations. Local development
  retains memory storage. No new dashboard configuration keys are needed.
- Public HTTPS DNS names and IP literals, including custom ports, are supported.
  Certificates must validate for that exact DNS name or IP. Private/loopback/link-
  local destinations are blocked; DNS results are checked and socket-pinned.
  No redirects, environmental proxies, URL credentials, queries or fragments.
- The hosted runtime needs outbound access to the endpoint on port 8081. Its owner
  must permit inbound access and maintain the certificate/token. Browser CORS is
  not required for this server-to-server call.
- Remote responses remain untrusted tool data. Failures produce safe messages
  for missing registration, missing connection, rejected tokens or unavailable
  service, without exposing remote bodies or credentials. No automatic retry.

Custom registrations use the existing registry schema (migration 004); no Delivery
schema upgrade or migration 005 is required for this flow. Compatibility code for
older DELIVERY-type registrations remains: those registrations can widen the role
constraint using fixed DDL, or an owner can apply migration 005 before creating
legacy DELIVERY entries. Do not rerun that migration on an upgraded database.

Registration after deployment takes effect immediately. No redeploy, dashboard
change or environment variable is needed to add this API or connect a token.
The supplier checks capability state on each turn: the delivery tool and carrier
description are offered to the model only when a selected connection matches an
active eligible registry entry. Delivery-option questions without that connection
receive a setup message, not a model-generated offer to look up carriers. Each
actual tool invocation checks the connection again, including deactivation or
endpoint changes made during model execution. Failed lookups cannot be replaced
by a model-generated distributor answer. OCI prompt guardrails still run first.
The app must first be deployed with this adapter code. Registry rows persist in
Oracle; session credentials use configured Redis or the shared Oracle connection
table. Local memory-cache credentials are lost on backend restart. Connections
expire with their session; a new login requires reconnecting. This fallback covers
delivery credentials only, not general session/history/workflow caching. Deployments
with multiple replicas still need shared Redis for those other features.

## Langfuse

With existing Langfuse configuration enabled on gateway and MCP, search the
project's trace/observation view for:

- `registry.create`, `registry.activate`, `registry.deactivate`, `registry.delete` for registry changes;
- `delivery.connect`, `delivery.disconnect` for supplier connection changes;
- `supplier.chatbot.request` and `mcp.ask_delivery_agent` for chat/tool execution;
- `delivery.ask` and `delivery.http` for delivery outcome and the external REST call.

Registry events identify the entry ID/type and status. Connection events omit the
token entirely. REST events include timing, remote request ID, answer status,
source count, model ID and demo flag. The existing MCP observation contains the
sanitized question/result. No authorization headers are passed to these
observations. Tracing failure does not prevent registration or chat. The remote
agent's internal AWS execution and token usage are not observable unless it
exposes/instruments them.
